## Shift from counting instructions to reconstructing possible control programs

A large original saved Minecraft world can encode software in several media: electrical/Redstone graph and mechanical state (hardware), command blocks and item/NBT/scoreboard predicates (instructions and memory), clickable chat JSON (human interface and externally supplied inputs), and player narratives (program specification). To recover what the gameplay does, we must reconstruct *exact control/data relationships* then compare them against creator guidance and historical player traces. Physical proximity alone cannot prove execution; a command text alone cannot prove what the player experienced.

The added disassembler is [`tools/reconstruct_legacy_core_command_controls.py`](../tools/reconstruct_legacy_core_command_controls.py). It reads only the exact pinned original ZIP and already pinned original graph, verifies **every original source tile-entity command SHA**, and consumes the independently qualified directed sensor graph. It adds these **typed source-static relations**:

1. **Exact scoreboard-objective references**: command writes; test/operation/selectors that read that objective; explicit historical 1.8 scoreboard grammar; never asserts that two selectors bind the same entity or score slot.
2. **Exact world-block state dependence**: `setblock` writes matched to `testforblock` readers of the same coordinate. Relative `~` coordinates are resolved only from a *source command block*, never from a player-click command with a dynamic player origin.
3. **Authored electrical control edges**: original `setblock ... redstone_block` writes can power a distinct adjacent source command block or a repeater/comparator rear input; independently verify exact originally authored point and legacy facing/port, not mere proximity.
4. **Actionable UI command graph**: all `tellraw` JSON parsed (bounded), `clickEvent`/run command verbs classified, click-to-block absolute targets checked, compared against source authors' other writers and exactly oriented hardware. The click action is an **authored input affordance**, not an observed player click.
5. **Nested execution shape**: bounded original Java 1.8 `execute ... [detect ...] <command>`, exposing nested operation family without acting on it or leaking original command text.
6. **Source subprogram grouping**: combine exact command-to-command power edges, same objective potential dependencies, same block write/test and qualified chain candidates into a directed graph. Recover weakly linked candidate instruction groups, sizes, named strict-sensor coverage and static directed/self-feedback cycles. Such groups are **not gameplay primitives** until an original-version runtime verifies the proposed mechanism.

**Derivative egress boundary:** original commands, JSON click body, scoreboard objective identifiers, locations, graph node IDs, clicked targets and source references remain *inside the ephemeral original workcell*; only aggregate source-class counts and nonpromotion statuses leave. The original full graph is not redistributed. Source historical clues were previously documented in [creator/user walkthrough evidence](legacy-core-author-player-walkthrough-evidence-20261025.md). Not even original HTML or recorded videos were downloaded into this source workcell.
